# Detection Engineering

## 1. Overview

The SOC Active Directory Detection Lab uses a custom detection-engineering approach to identify suspicious authentication activity, account and privilege changes, credential-access techniques, discovery activity, lateral movement, persistence, defense evasion, and impact-related activity across a Windows Active Directory environment.

The detection layer is implemented using **Wazuh custom rules** and Windows telemetry collected from domain infrastructure and endpoints. The rules are designed to build upon native Wazuh decoding and detection capabilities by adding environment-specific logic, event-field matching, correlation, severity classification, and MITRE ATT&CK mappings.

The project contains **42 custom detection rules**, organized into eight security-relevant categories:

- Authentication
- Account Management
- Privilege Escalation
- Credential Access and Kerberos
- Discovery and Reconnaissance
- Lateral Movement and Remote Execution
- Persistence and Defense Evasion
- Impact

The detections are developed and validated within a controlled lab environment consisting of a Windows Server 2022 domain controller, Windows 11 endpoint, Wazuh server, and Kali Linux attack-simulation system.

---

# 2. Detection Engineering Approach

The detection engineering approach follows a telemetry-first methodology.

Rather than creating rules solely around attack names, each detection is developed by identifying the observable Windows or Sysmon telemetry associated with a behavior and then translating that telemetry into Wazuh detection logic.

The general approach is:

```text
Threat / ATT&CK Technique
        ↓
Identify Windows/Sysmon Telemetry
        ↓
Identify Relevant Event Fields
        ↓
Review Existing Wazuh Rules
        ↓
Develop Custom Rule
        ↓
Syntax / Configuration Validation
        ↓
Controlled Attack Simulation
        ↓
Verify Raw Telemetry
        ↓
Verify Custom Alert
        ↓
Investigation Validation
        ↓
Document Detection
        ↓
Tune / Refine
```

This approach allows the project to maintain a direct relationship between:

```text
Threat Behavior
      ↓
Telemetry
      ↓
Detection Logic
      ↓
Wazuh Alert
      ↓
MITRE ATT&CK Technique
      ↓
Investigation
```

# 5. Wazuh Custom Rules

The project implements **42 custom Wazuh detection rules**.

The rules are stored in:

```text
detection-rules/
└── Wazuh-Rules.xml
```

The custom rules use Wazuh capabilities including:

- Parent-rule dependencies
- `if_sid`
- `if_matched_sid`
- `if_group`
- Field matching
- PCRE2 matching
- Frequency-based correlation
- Time-window correlation
- Same-field correlation
- Rule chaining
- Severity levels
- Rule groups
- MITRE ATT&CK metadata

The rules use custom identifiers in the `100100`–`100141` range.

For example, DET-002 depends on DET-001 and correlates failed-authentication events by target username, using a frequency of three events within 120 seconds.

This allows the detection to move beyond individual failed-authentication events and identify a potential brute-force pattern.

# 6. Detection Lifecycle

The detection lifecycle used in the project consists of the following stages:

```text
1. Identify Threat Behavior
        ↓
2. Map to ATT&CK Technique
        ↓
3. Identify Observable Telemetry
        ↓
4. Identify Relevant Event Fields
        ↓
5. Develop Detection Logic
        ↓
6. Validate Rule Syntax
        ↓
7. Generate Controlled Activity
        ↓
8. Verify Raw Telemetry
        ↓
9. Verify Wazuh Ingestion
        ↓
10. Validate Detection Alert
        ↓
11. Validate Investigation Context
        ↓
12. Tune Detection
        ↓
13. Document Detection
```

Each stage provides a checkpoint before a detection is considered validated.

The lifecycle is designed to ensure that a detection is supported by actual telemetry generated within the lab rather than being based only on theoretical attack behavior.

# 7. Detection Development Process

The project's detection development process is:

```text
Threat / ATT&CK Technique
        ↓
Identify Windows/Sysmon Telemetry
        ↓
Identify Relevant Event Fields
        ↓
Review Existing Wazuh Rules
        ↓
Develop Custom Rule
        ↓
Syntax / Configuration Validation
        ↓
Controlled Attack Simulation
        ↓
Verify Raw Telemetry
        ↓
Verify Custom Alert
        ↓
Investigation Validation
        ↓
Document Detection
        ↓
Tune / Refine
```

## Step 1 — Threat / ATT&CK Technique

The detection begins with a security behavior or ATT&CK technique that should be observable in the environment.

## Step 2 — Identify Windows/Sysmon Telemetry

The relevant Windows event source or Sysmon telemetry is identified.

Examples include:

- Security Event Log
- Sysmon
- PowerShell
- Windows Defender
- Firewall
- System events
- Application events

## Step 3 — Identify Relevant Event Fields

The fields required to distinguish the behavior are identified.

Examples from the custom rules include:

```text
win.system.eventID
win.eventdata.targetUserName
win.eventdata.ipAddress
win.eventdata.commandLine
win.eventdata.image
win.eventdata.originalFileName
win.eventdata.logonType
win.eventdata.objectDN
win.eventdata.subjectUserName
```

## Step 4 — Review Existing Wazuh Rules

Existing Wazuh rules are reviewed to determine whether the required event has already been decoded or detected by a built-in rule.

The custom detection can then use an existing rule as its parent rather than independently processing the raw event.

## Step 5 — Develop Custom Rule

Custom detection logic is created using the appropriate Wazuh rule constructs.

Depending on the detection, this may involve:

- Parent rules
- Event IDs
- Specific event fields
- Regex
- PCRE2
- Frequency
- Timeframes
- Same-field correlation
- Rule chaining

## Step 6 — Syntax / Configuration Validation

The rule configuration is validated before testing.

This ensures that the custom rule can be loaded correctly and that its XML and Wazuh rule syntax are valid.

## Step 7 — Controlled Attack Simulation

The relevant behavior is generated in the controlled lab environment.

Kali Linux is used as the attack-simulation system where appropriate.

## Step 8 — Verify Raw Telemetry

The underlying Windows/Sysmon event is verified.

This step confirms that the expected telemetry was actually generated.

## Step 9 — Verify Custom Alert

The resulting Wazuh alert is checked to confirm that the custom rule matched the expected activity.

## Step 10 — Investigation Validation

The alert is reviewed to ensure that relevant investigation fields are available.

Examples include:

- Username
- Source IP
- Destination system
- Process
- Command line
- Event ID
- Object
- Group
- Authentication information

## Step 11 — Document Detection

The validated detection is documented as an individual detection entry.

## Step 12 — Tune / Refine

The detection is refined where necessary based on the telemetry and alert results.

# 9. MITRE ATT&CK Integration

MITRE ATT&CK mappings are incorporated directly into the Wazuh custom rules.

The mappings are represented using Wazuh's `<mitre>` rule element.

Example:

```xml
<mitre>
    <id>T1110</id>
</mitre>
```

The associated rule groups also identify ATT&CK techniques using tags such as:

```text
attack.t1110
attack.t1078
attack.t1098
attack.t1558.003
attack.t1003.006
attack.t1021.002
attack.t1059.001
```

Some detections map to multiple techniques.

For example, DET-004 maps successful login after failed attempts to both T1110 and T1078.

This allows the detection layer to maintain a relationship between observed telemetry and the ATT&CK techniques represented by the behavior.

The MITRE mapping is therefore integrated at the rule level rather than maintained only as an external documentation table.

# 10. Detection Validation Approach

All custom detections are tested and validated within the controlled lab environment.

The validation methodology is:

```text
1. Generate controlled activity
        ↓
2. Confirm Windows/Sysmon event
        ↓
3. Confirm Wazuh ingestion
        ↓
4. Confirm parent/built-in rule where applicable
        ↓
5. Confirm custom detection rule
        ↓
6. Verify alert fields
        ↓
7. Verify MITRE mapping
        ↓
8. Document expected alert
        ↓
9. Clean up test activity
```

## 10.1 Generate Controlled Activity

The required behavior is generated intentionally within the lab.

## 10.2 Confirm Windows/Sysmon Event

The underlying event is checked to verify that the expected telemetry exists.

## 10.3 Confirm Wazuh Ingestion

The event is verified as successfully reaching the Wazuh monitoring pipeline.

## 10.4 Confirm Parent/Built-in Rule

Where a custom detection depends on an existing Wazuh rule, the parent rule is verified.

This is particularly important for rules using constructs such as:

```xml
<if_sid>
<if_matched_sid>
<if_group>
```

## 10.5 Confirm Custom Detection

The custom rule is verified to match the intended activity.

## 10.6 Verify Alert Fields

The resulting alert is checked for relevant investigation fields.

## 10.7 Verify MITRE Mapping

The generated alert is checked to confirm that the expected MITRE ATT&CK mapping is present.

## 10.8 Document Expected Alert

The expected detection behavior and alert characteristics are documented.

## 10.9 Clean Up Test Activity

Test accounts, processes, persistence mechanisms, configuration changes, and other temporary artifacts are removed where applicable.

# 11. Detection Tuning

Detection tuning is performed based on observed telemetry and detection behavior.

The project considers the following tuning areas.

## 11.1 Parent-Rule Dependencies

Custom rules may depend on existing Wazuh rules.

The parent rule must generate the expected event before the child/custom detection can operate.

## 11.2 Event-Field Selection

The detection logic is refined around fields that provide useful and reliable discrimination.

Examples include:

```text
win.system.eventID
win.eventdata.targetUserName
win.eventdata.ipAddress
win.eventdata.commandLine
win.eventdata.image
win.eventdata.originalFileName
win.eventdata.logonType
```

## 11.3 Regex / PCRE2 Matching

PCRE2 matching is used where more precise pattern matching is required.

Examples include executable paths, command-line parameters, usernames, logon types, and event identifiers.

## 11.4 False-Positive Considerations

Detection logic is reviewed against benign activity to determine whether normal administrative or system behavior can trigger the rule.

The goal is to retain useful detection coverage while reducing unnecessary alerts.

## 11.5 Severity Selection

Wazuh rule levels are selected according to the expected security significance of the detected behavior.

The custom rules use different levels depending on the detection.

## 11.6 Rule Chaining

Rule chaining is used where a detection is more meaningful when built on previously matched activity.

Examples include:

```text
Base Event
    ↓
Parent Wazuh Rule
    ↓
Custom Detection
```

and:

```text
Failed Authentication
        ↓
Multiple Failures
        ↓
Successful Authentication
        ↓
Successful Login After Failed Attempts
```

## 11.7 Archive vs Alert Index Distinction

The validation process considers the distinction between archived event data and generated alerts.

This helps determine whether:

- The Windows event was ingested
- The event was decoded
- The parent rule matched
- The custom rule matched
- An alert was actually generated

This distinction is important when troubleshooting a detection that does not produce an expected alert.

## 11.8 Benign vs Suspicious Variants

Rules are tested against both expected suspicious behavior and benign variants where applicable.

This helps determine whether the detection logic is sufficiently specific for the intended behavior.

## 11.9 Refining Rules When Expected Telemetry Is Not Generated

Detection development does not assume that the expected telemetry will always be generated exactly as initially anticipated.

When expected telemetry is missing or differs from the expected structure, the rule can be refined based on the actual event fields generated by the Windows environment.

This creates a feedback loop:

```text
Detection Design
      ↓
Test Activity
      ↓
Observed Telemetry
      ↓
Rule Refinement
      ↓
Retest
      ↓
Validated Detection
```

# 12. Detection Engineering Design Principles

The project's custom detections follow several core principles.

### Telemetry-driven

Rules are based on observable Windows and Sysmon telemetry.

### Modular

Each detection has an individual DET identifier and can be documented and validated independently.

### Correlation-aware

Where appropriate, multiple events are correlated using fields, frequency, and timeframes.

### MITRE-aligned

Detections include MITRE ATT&CK mappings directly within the Wazuh rule definitions.

### Investigation-oriented

Alert descriptions include useful context such as usernames, IP addresses, command lines, processes, objects, and event identifiers where available.

### Validated in a controlled environment

The custom detections are tested using controlled activity within the lab environment.

### Tunable

Rules can be refined based on actual telemetry, false-positive considerations, parent-rule behavior, and validation results.
