# IR-003 — Kerberos & Credential Theft Attack

## 1. Objective

Provide an operational response workflow for suspected Kerberos abuse and credential-theft activity identified by Wazuh across the Active Directory environment.

This playbook helps analysts determine whether Kerberoasting, AS-REP Roasting, DCSync, forged Kerberos tickets, LSASS credential dumping, NTDS.dit extraction, or Pass-the-Hash activity represents benign administrative activity, a confirmed credential-access attempt, or broader domain compromise. The workflow covers triage, incident scoping, containment, credential remediation, eradication, recovery, and validation.

---

## 2. Scope & Related Detections

### 2.1 Scope

This playbook applies to:

- `DC01` — Active Directory Domain Controller
- `CLIENT01` — Domain-joined Windows endpoint
- Domain user, service, and privileged accounts
- Kerberos authentication and service-ticket activity
- Active Directory directory replication activity
- Windows credential stores and authentication processes
- NTDS.dit and related credential material
- NTLM network authentication associated with potential Pass-the-Hash activity
- Wazuh alerts generated by the related custom detections

### 2.2 Related Detection Rules

| Detection | Description | Wazuh Rule | Severity | Primary Event |
|---|---|---:|---:|---|
| DET-017 | Kerberos Service Ticket Request / Possible Kerberoasting | 100116 | High | 4769 |
| DET-018 | AS-REP Roasting | 100117 | High | 4768 |
| DET-019 | Directory Replication Request / Possible DCSync | 100118 | Critical | 4662 |
| DET-020 | Golden Ticket Attack | 100119 | Critical | 4769 |
| DET-021 | Silver Ticket Attack | 100120 | High | 4624 |
| DET-022 | LSASS Credential Dumping | 100121 | High | Sysmon 10 |
| DET-023 | NTDS.dit Credential Dumping via ntdsutil IFM | 100122 | Critical | Sysmon 1 / 4688 |
| DET-024 | Pass-the-Hash | 100123 | High | 4624 |

### 2.3 Detection-to-Incident Relationship

These detections are individual indicators of potentially malicious credential access or authentication abuse. A single alert does not automatically establish compromise.

The incident-level investigation should determine whether:

```text
Single Detection
      ↓
Suspicious Credential / Kerberos Activity
      ↓
Correlate Identity + Source + Host + Related Detections
      ↓
Determine Credential Exposure
      ↓
Determine Lateral Movement / Persistence
      ↓
Assess Domain-Level Impact
```

Multiple detections occurring against the same account, host, or time window should be treated as a stronger indication of an active attack chain.

## 3. Attack Scenario

### 3.1 Scenario Overview

An adversary obtains or attempts to obtain Active Directory credentials and authentication material. Depending on the attack path, the adversary may request service tickets for offline cracking, target accounts without Kerberos pre-authentication, abuse directory replication privileges, forge Kerberos tickets, access LSASS memory, extract `ntds.dit`, or reuse stolen NTLM hashes for lateral movement.

Credential theft in this category can escalate rapidly from a single endpoint compromise to domain-wide compromise, particularly when privileged credentials, service-account secrets, the `krbtgt` account, or Active Directory database contents are exposed.

### 3.2 Typical Attack Flow

```text
Initial Access / Compromised Account or Endpoint
                    ↓
        Credential Access Attempt
                    ↓
 ┌──────────────────┼──────────────────┐
 ↓                  ↓                  ↓
Kerberoasting    AS-REP Roasting   LSASS Dumping
 ↓                  ↓                  ↓
Service/Account   Kerberos Secrets  User Credentials
Ticket Material       ↓                  ↓
 ↓                    └────────┬─────────┘
 └─────────────────────────────┤
                               ↓
                    Privileged Credential Access
                               ↓
              ┌────────────────┼────────────────┐
              ↓                ↓                ↓
           DCSync         NTDS.dit Theft    Ticket Forgery
              ↓                ↓                ↓
              └────────────────┼────────────────┘
                               ↓
                   Credential Reuse / PtH
                               ↓
                    Lateral Movement
                               ↓
                    Domain Compromise
```

This represents a possible attack path, not a guaranteed detection sequence.

### 3.3 Expected Detection Sequence

Potential sequences include:

**Kerberos credential harvesting**

```text
DET-017 / DET-018
        ↓
Suspicious Kerberos ticket activity
        ↓
Credential material obtained or targeted
        ↓
Credential reuse / further authentication
```

**Endpoint credential dumping**

```text
DET-022
        ↓
LSASS access
        ↓
Credential material potentially exposed
        ↓
Suspicious authentication / lateral movement
        ↓
DET-024 or related detections
```

**Domain credential compromise**

```text
DET-019 or DET-023
        ↓
Domain credential database / replication abuse
        ↓
Potential exposure of domain-wide credentials
        ↓
Privileged authentication / ticket abuse
        ↓
Possible lateral movement
```

### 3.4 Potential Impact

Potential impact includes:

- Exposure of user or service-account credentials
- Theft of NTLM hashes or Kerberos keys
- Unauthorized access to privileged accounts
- Forged Kerberos authentication
- Lateral movement between domain systems
- Compromise of service accounts
- Compromise of Domain Admin or equivalent privileges
- Exposure of the Active Directory credential database
- Domain-wide authentication compromise
- Long-term attacker persistence through stolen authentication material

## 4. Initial Triage

### 4.1 Alert Validation

When an alert triggers:

- Identify the DET ID and Wazuh rule ID.
- Review the complete Wazuh alert and raw Windows/Sysmon event.
- Record the timestamp.
- Identify the affected Wazuh agent.
- Identify the account involved.
- Identify source IP, source host, or originating process where available.
- Record relevant command-line, process, Kerberos, or authentication fields.
- Determine whether the activity is expected and authorized.

Pay particular attention to DET-019 and DET-023. Directory replication abuse or NTDS.dit extraction can indicate a high-risk domain compromise even when only one alert is initially visible.

### 4.2 Identify Affected Assets

Determine whether activity involves:

- `DC01`
- `CLIENT01`
- Another domain endpoint represented in Wazuh
- A domain controller or privileged administrative workstation
- A service account or privileged account

Activity occurring directly on `DC01` should receive elevated scrutiny because the system contains critical Active Directory security material.

### 4.3 Identify Affected Identity

Determine:

- Target account
- Source/executing account
- Whether the account is privileged
- Whether it is a service account
- Whether the account was recently created, enabled, reset, or modified
- Whether the account has recently authenticated from an unusual system

Correlate with the **Active Directory Security** and **Authentication & Account Monitoring** dashboards where appropriate.

### 4.4 Identify Attack Source

Establish:

- Source IP address
- Workstation name
- Source process
- Parent process
- Command line
- Source endpoint
- Whether the source is an authorized administrative system

For LSASS and NTDS.dit activity, inspect the originating process and execution context.

### 4.5 Establish Initial Timeline

Record:

| Time | Detection/Event | Host | User | Source | Finding |
|---|---|---|---|---|---|
| `<time>` | `<event>` | `<host>` | `<user>` | `<source>` | `<finding>` |

Search before and after the triggering event to identify related authentication, process, Kerberos, directory, and lateral-movement activity.

### 4.6 Determine Whether Activity Is Expected

Potentially legitimate activity can include:

- Authorized Active Directory administration
- Approved service-account operations
- Legitimate Kerberos service-ticket activity
- Authorized troubleshooting or memory-dump operations
- Approved Domain Controller deployment/maintenance using IFM
- Legacy applications legitimately using NTLM

Do not close the incident solely because the executable or Windows event is legitimate. Validate the **user, host, timing, command line, purpose, and authorization**.

## 5. Investigation Workflow

### 5.1 Establish the Initial Event

Determine exactly what triggered the detection.

For Kerberos-related alerts, review the relevant ticket request fields and determine the targeted account/service.

For DCSync, determine the account performing the directory replication request and the target domain-controller context.

For LSASS dumping, inspect the source process, target process, access mask, and call trace.

For NTDS.dit extraction, inspect the `ntdsutil.exe` command line and output directory.

For Pass-the-Hash, verify the authentication context, particularly NTLM network authentication and Logon Type 3 where present.

### 5.2 Investigate the Source

Determine whether the source is:

- A normal user workstation
- An administrative workstation
- `CLIENT01`
- `DC01`
- A known management system
- An unexpected or compromised endpoint

For process-based detections, correlate with Sysmon Event ID 1 process creation.

For LSASS access, inspect:

- `win.eventdata.sourceImage`
- `win.eventdata.sourceProcessId`
- `win.eventdata.grantedAccess`
- `win.eventdata.callTrace`
- Parent process and command line

Suspicious tools or execution from temporary/user-writable locations should increase confidence of malicious activity.

### 5.3 Investigate the Account / Identity

Review:

- Account name
- Domain
- Privilege level
- Group memberships
- Recent successful and failed logons
- Recent password changes/resets
- Recent account modifications
- Service-account status
- Whether the account normally performs the observed activity

For privileged accounts, assume greater risk because stolen credentials may enable rapid escalation and lateral movement.

### 5.4 Investigate the Affected Host

For `CLIENT01`:

- Review recent process creation
- Check for suspicious PowerShell, command shell, credential-access tools, or remote-execution activity
- Search for dump files or staging directories
- Review recent network authentication activity

For `DC01`:

- Review all nearby credential-access activity
- Check for unauthorized administrative commands
- Search for suspicious processes and command lines
- Review directory replication events
- Review NTDS-related activity
- Review privileged account authentication
- Avoid unnecessary actions that could interrupt Active Directory availability

Use the **Sysmon Endpoint Activity** dashboard for process and endpoint activity and the **SOC Detection Overview** dashboard for related detection activity.

### 5.5 Correlate Related Detection Activity

Search for detections occurring around the same time, particularly:

- DET-017 / DET-018 — Kerberos credential harvesting
- DET-019 — DCSync
- DET-020 / DET-021 — Forged Kerberos tickets
- DET-022 — LSASS credential dumping
- DET-023 — NTDS.dit extraction
- DET-024 — Pass-the-Hash
- Authentication detections from IR-001
- Account/privilege changes from IR-002
- Lateral-movement detections from IR-005

A sequence such as:

```text
LSASS / NTDS Credential Access
        ↓
Privileged Authentication
        ↓
NTLM Network Logon
        ↓
Remote Execution
```

provides substantially stronger evidence of compromise than an isolated authentication event.

### 5.6 Build the Attack Timeline

Construct a chronological timeline containing:

1. First suspicious authentication or process
2. Credential-access activity
3. Kerberos or directory activity
4. Privilege-related activity
5. Credential reuse
6. Lateral movement
7. Persistence, if present
8. Most recent attacker activity

Record timestamps using the Wazuh event time and preserve the original event details where possible.

### 5.7 Determine Attack Scope

Determine whether compromise is limited to:

- One user account
- One service account
- One endpoint
- Multiple endpoints
- One privileged account
- Multiple privileged accounts
- `DC01`
- The Active Directory domain

For credential-theft incidents, scope must include **potentially exposed credentials**, not only systems where alerts were generated.

### 5.8 Determine Evidence of Compromise

Treat the incident as stronger evidence of confirmed compromise when one or more of the following are present:

- Unauthorized credential dumping
- Unauthorized NTDS.dit extraction
- Unauthorized directory replication
- Confirmed forged-ticket use
- Stolen credentials reused from an unexpected host
- Pass-the-Hash activity from a compromised source
- Credential-theft tooling executed by an unauthorized account
- Multiple related detections forming a coherent attack chain
- Privileged credentials demonstrably exposed

## 6. Incident Assessment

### 6.1 Suspicious Activity

Examples:

- Unusual Kerberos ticket requests
- Unexpected NTLM authentication
- LSASS access from an uncommon process
- `ntdsutil.exe` IFM execution outside approved maintenance
- Directory replication activity from an account that does not normally perform it

### 6.2 Confirmed Malicious Activity

Examples:

- Credential-dumping tooling executed without authorization
- Kerberoasting or AS-REP Roasting activity with malicious intent established
- Forged-ticket indicators correlated with unauthorized access
- DCSync from an unauthorized principal
- NTDS.dit extraction by an attacker
- Pass-the-Hash activity linked to a compromised source

### 6.3 Confirmed Compromise

Consider compromise confirmed when evidence demonstrates that attacker-controlled activity obtained or used credential material, particularly where:

- Privileged credentials were exposed
- Domain credentials were extracted
- Stolen hashes were reused
- Forged Kerberos tickets were successfully used
- Multiple hosts were accessed using compromised credentials
- `DC01` or domain-level security material was compromised

### 6.4 Severity Considerations

Increase incident severity when:

- `DC01` is involved
- Domain Admin or Enterprise Admin credentials are exposed
- `krbtgt` credentials may be compromised
- DCSync or NTDS.dit extraction is confirmed
- Multiple accounts or hosts are affected
- Credential material was successfully reused
- Lateral movement is observed
- Persistence or defense evasion is present
- Domain-wide compromise cannot be excluded

---

## 7. Containment

### 7.1 Immediate Containment

If malicious activity is active:

- Stop the attacker-controlled process where safe to do so.
- Isolate a compromised endpoint such as `CLIENT01` when appropriate.
- Prevent continued access from the identified attacker source.
- Preserve relevant evidence before destructive cleanup where practical.

Avoid immediately isolating `DC01` unless the incident requires it and the impact on Active Directory availability has been considered.

### 7.2 Account Containment

For compromised accounts:

- Disable or lock the affected account when appropriate.
- Force a password reset.
- Reset service-account credentials if exposed.
- Remove unauthorized privileged access.
- Terminate active sessions where supported and appropriate.
- Review other accounts that may have been exposed through the same credential-theft activity.

### 7.3 Endpoint Containment

For a compromised endpoint:

- Isolate `CLIENT01` from the network.
- Stop malicious processes.
- Preserve relevant process, event, and file evidence.
- Restrict access to identified attacker infrastructure where applicable.

For `DC01`, prioritize maintaining domain availability while preventing further attacker activity.

### 7.4 AD Containment

If domain-level credential compromise is suspected:

- Restrict compromised administrative accounts.
- Remove unauthorized privileged memberships.
- Prevent compromised accounts from authenticating until remediated.
- Review privileged authentication across the domain.
- Treat exposed domain credentials as potentially reusable until reset.

### 7.5 Additional Containment Actions

Where confirmed domain credential compromise exists:

- Reset affected privileged credentials.
- Reset credentials for accounts whose authentication material was exposed.
- Review service accounts associated with affected systems.
- Identify and contain additional endpoints showing related activity.
- Consider broader credential remediation when the blast radius cannot be reliably bounded.

---

## 8. Eradication

### 8.1 Remove Attacker Access

- Remove unauthorized accounts or access paths.
- Remove unauthorized privileged group membership.
- Revoke compromised credentials.
- Remove unauthorized administrative access.

### 8.2 Remove Persistence / Malicious Artifacts

- Remove credential-dumping tools.
- Remove malicious scripts and executables.
- Remove staged credential dumps.
- Remove unauthorized scheduled tasks, services, or other persistence discovered during investigation.
- Remove temporary dump files and staged NTDS artifacts after required evidence preservation.

### 8.3 Remediate Compromised Credentials

Credential remediation must reflect the type of material potentially exposed.

Examples:

- User password reset after LSASS compromise
- Service-account password reset after credential exposure
- Privileged-account password reset after credential theft
- Broader domain credential remediation when NTDS.dit or DCSync exposure is confirmed

If the `krbtgt` account is determined to be compromised, follow the organization's approved Active Directory recovery procedure for resetting it and invalidating forged Kerberos tickets. Do not perform an unplanned `krbtgt` reset on a production domain without assessing replication and authentication impact.

### 8.4 Restore Unauthorized Changes

Review and revert unauthorized:

- Account changes
- Group membership changes
- AD object modifications
- Authentication configuration changes
- Security-control changes
- Other attacker-created access mechanisms

---

## 9. Recovery & Validation

### 9.1 System Recovery

- Return contained endpoints to normal network operation only after remediation.
- Verify required services and applications operate normally.
- Confirm no malicious processes remain active.

### 9.2 Account / AD Recovery

- Verify compromised accounts are secured.
- Verify privileged group memberships.
- Confirm unauthorized accounts and access paths are removed.
- Confirm required service accounts function after credential rotation.
- Verify Active Directory replication and authentication remain healthy.

### 9.3 Security Control Recovery

Verify that:

- Windows security logging is functioning.
- Sysmon is running and producing expected telemetry.
- Wazuh is receiving Windows and Sysmon events.
- Security controls have not been disabled or modified.
- Relevant detection rules remain enabled.

### 9.4 Telemetry Validation

Use Wazuh to confirm that post-recovery telemetry is still visible.

Validate relevant sources such as:

- Kerberos events
- Authentication events
- Directory service events
- Sysmon process/process-access events
- Wazuh custom detections

Re-test affected detection coverage when appropriate, particularly after security-control or logging changes.

### 9.5 Post-Recovery Monitoring

Monitor for recurrence of:

- Kerberos ticket anomalies
- Directory replication requests
- LSASS access
- NTDS-related activity
- NTLM authentication
- Privileged logons
- Lateral movement
- Reappearance of attacker tooling

Maintain heightened monitoring until the absence of continued compromise is reasonably established.

## 10. Escalation Criteria

### 10.1 Escalate When

Escalate to a senior analyst or incident lead when:

- Credential theft is confirmed
- A privileged account is compromised
- Multiple hosts or accounts are affected
- Lateral movement is observed
- Attack tooling is identified
- The source endpoint cannot be confidently contained
- The scope of credential exposure is uncertain

### 10.2 High-Risk Conditions

Immediate high-priority escalation is warranted for:

- DET-019 / confirmed DCSync
- DET-023 / confirmed NTDS.dit extraction
- Confirmed Golden Ticket activity
- Confirmed compromise of Domain Admin or Enterprise Admin credentials
- Compromise of `krbtgt`
- Multiple privileged credentials exposed
- Credential theft followed by successful lateral movement
- Evidence of domain-wide authentication compromise

### 10.3 Domain-Level Compromise Indicators

Treat the incident as potentially domain-wide when:

- DCSync succeeds or is strongly confirmed
- `ntds.dit` and `SYSTEM` credential material are extracted
- Multiple privileged accounts are exposed
- Forged Kerberos tickets are successfully used
- Compromised credentials authenticate across multiple domain systems
- The original compromised source cannot be reliably identified or contained

## 11. Closure Criteria

### 11.1 Investigation Complete

- Initial detection validated.
- Attack method identified.
- Source, identity, and affected systems determined.
- Attack timeline documented.
- Related detections correlated.

### 11.2 Containment Complete

- Active attacker access stopped.
- Compromised endpoints contained.
- Compromised accounts secured.
- Unauthorized privileged access removed.

### 11.3 Eradication Complete

- Credential-theft tools removed.
- Malicious artifacts removed.
- Unauthorized changes reverted.
- Persistence removed.
- Required credentials rotated.

### 11.4 Recovery Complete

- Systems and accounts returned to normal operation.
- Active Directory functionality verified.
- Required service accounts operational.
- Security controls restored.

### 11.5 Validation Complete

- Windows logging functioning.
- Sysmon telemetry functioning.
- Wazuh telemetry confirmed.
- Relevant custom detections remain operational.
- No continuing credential-theft or authentication anomalies observed.

### 11.6 Final Documentation

Document:

- Initial detection
- Attack technique
- Affected accounts and systems
- Credential material potentially exposed
- Attack source
- Timeline
- Scope and blast radius
- Containment actions
- Eradication actions
- Credential remediation
- Recovery and validation results
- Remaining risks or monitoring requirements

## Analyst Decision Flow

```text
Wazuh Alert
    ↓
Validate Detection
    ↓
Identify Host + User + Source
    ↓
Expected / Authorized?
    ├── Yes → Document → Monitor / Close
    │
    └── No / Unclear
             ↓
      Correlate Related Events
             ↓
      Credential Material Exposed?
        ├── No → Suspicious / Malicious Activity
        │
        └── Yes
             ↓
      Credential Compromise
             ↓
      Lateral Movement / Privilege Abuse?
        ├── No → Contain + Eradicate + Recover
        │
        └── Yes
             ↓
      Assess Domain-Level Impact
             ↓
      Contain Accounts + Endpoints
             ↓
      Remediate Credentials
             ↓
      Restore + Validate Telemetry
             ↓
      Heightened Monitoring
             ↓
          Close
```
